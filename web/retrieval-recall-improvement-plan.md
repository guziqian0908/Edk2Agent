# EDK2 知识库检索召回优化方案（关联内容漏召回治理）

> 目标：系统性解决"问题与文档**语义相关、但表层用词不一致**，导致向量检索截断、最终答案质量下降"的通用性召回缺口。
> 范围：检索编排层（不改向量库也能落地大部分收益）。

---

## 1. 背景与问题

当前 Web 问答服务在检索阶段存在一个**通用性召回缺口**：当问题与某篇文档"语义相关但表层用词不一致"时，双编码器（bi-encoder）向量检索因余弦距离过远而将其截断在 `top_k` 之外，大模型拿不到关键依据，结果要么答偏、要么因依据不足而退化重复。

**典型案例**：`uefi driver binding version 可以用来做什么`
- 知识库中 `3141_connectcontroller.md` 及其同区文档（`3142` 选项 ROM 示例、`91` 结构体定义、UEFI 规范 `11_Protocols`）**确实包含** "Version 字段决定 ConnectController 连接优先级" 这一相关知识；
- 但查询核心是 "version"，向量把它锚定到 "Driver Supported EFI Version Protocol" 等文档，而 `3141`（讲连接流程）因不含 "version" 直白字眼，跌出召回线；
- 结果：最相关的连接过程文档未被送入大模型，模型无话可说 → 退化重复。

这并非个例，而是向量检索的固有局限：**只对齐表层/语义用词，不擅长"相关但措辞不同"的桥接**。

---

## 2. 根因

1. 双编码器相似度 = 查询向量 vs 文档向量，对"用词鸿沟"敏感；
2. 第一关 `top_k` 截断过窄，相关文档在精排前就被丢弃；
3. 查询仅做翻译/轻量改写，缺乏"关联概念"扩展；
4. 文档间结构关系（同章节/父子节）未被利用来兜底。

---

## 3. 四层解法框架

| 层 | 方向 | 代表技术 |
|----|------|----------|
| **L1 查询侧** | 把"意图"展开成多面检索 | 关系型查询扩展、HyDE（假设答案嵌入）、意图消歧 |
| **L2 检索架构** | 先广撒网再精排序 | 加宽召回 + 强重排器（cross-encoder）、混合检索（BM25+向量, RRF 融合） |
| **L3 结构/图谱** | 用文档"关系"兜底 | 目录邻居扩展（SUMMARY.md 章节层级）、元数据路由 |
| **L4 索引质量** | 让 chunk 自带上下文 | 章节感知分块 + 重叠、评测闭环 |

---

## 4. 优先级排序与理由

按 **ROI（收益/成本）、风险、对现有架构侵入度** 排序：

### P0 — 关系型查询扩展（最高优先）
- **收益**：直接修复已观测失效；通用性强（任何"用词鸿沟"类问题都受益）。
- **成本**：低。现有代码已有多路 `/search` 骨架（`engQuery` / `docsQuery` / `fq` / `sq`），只需把"翻译"升级为"翻译 + 关联概念扩展"，多发 2–3 路查询。例如 `version` → 同时检索 `ConnectController priority ordering`、`Driver Binding Protocol Version field`、`driver connection precedence`。
- **风险**：低（不改向量库，仅改检索编排与 prompt）。
- **关键**：扩展词由 LLM 基于"问题意图 + 知识库章节结构"生成，而非死规则。

### P1 — 加宽召回 + 强化重排
- **收益**：从架构上消除"第一关过窄导致相关文档被截"；重排器能识别"相关但用词不对齐"的文档。
- **成本**：中。需调 `top_k`（如 10→30~50）并评估/增强 cross-encoder 重排器（现有 `RERANK_COVERAGE_THRESHOLD` / rerank 逻辑可扩展）。
- **风险**：中。召回过宽会增加 token 与噪声，需重排器与 `lowCoverage` 门控兜底。
- **关键**：先广后精——宽召回必须由强重排收敛。

### P2 — 目录邻居扩展（SUMMARY.md 结构兜底）
- **收益**：精准命中"内容相关但无直白字段"的场景；利用已有章节层级（`SUMMARY.md` 已在库中）。
- **成本**：低。命中某章节文档时，拉取其同父节/兄弟节文档（如 `3141 ↔ 3142 ↔ 91`）。
- **风险**：低。
- **关键**：作为 P0 多查询的补充兜底，几乎零额外检索成本（从已召回结果推导）。

### P3 — 索引/分块优化 + 混合检索
- **收益**：长期根因治理（chunk 自带章节上下文、BM25 兜关键词）。
- **成本**：高。需重建索引（当前 KB ~16G）、引入/融合 BM25。
- **风险**：高（重建耗时、可能引入噪声）。
- **关键**：放到后面，作为质量深化，非当务之急。

---

## 5. 本项目落地路线图

- **阶段一（P0 + P2，约 1–2 天）**：关系型查询扩展 + 目录邻居扩展。改动集中于 `web/server.js` 的检索编排与扩展 prompt。预期：关联类问题召回显著改善。
- **阶段二（P1，约 2–3 天）**：加宽 `top_k` + 强化/评估重排器；建立 golden query 评测集与 recall 指标（利用现有 `emitTrace` 可观测性）。
- **阶段三（P3，按需）**：分块策略调整 + 混合检索，必要时重建索引。

---

## 6. 预期收益与度量

- **指标**：golden query 集的 `recall@k`、答案相关性人工评分、退化重复率（本次已加 `answer_revision` / 截断 / 重试守卫，可联动观测）。
- **预期**：P0 + P2 即可消除大部分"相关却漏召回"；P1 进一步抬升上限。

---

## 7. 风险与权衡

- 召回变宽 → token 成本上升、噪声上升 → 靠重排与 `lowCoverage` 门控平衡。
- 扩展词过多 → 引入无关文档 → 限制扩展路数（2–3）并加权。
- 不急于重建向量库（P3），优先用"编排层"低成本解决。

---

## 8. 结论

最高性价比路径：**先在查询侧做关系型扩展（P0）+ 目录邻居兜底（P2）**，再用"加宽 + 重排"（P1）收口；索引重建（P3）作为长期深化。整体**不改动向量库**即可显著改善"相关但被忽略"的问题。
