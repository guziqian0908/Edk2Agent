Q: EDK II 里的 INF / DEC / DSC / FDF 四个元数据文件各自负责什么？模块(Module)、包(Package)、平台(Platform)又是什么关系？
A: 模块是最小的可独立编译单元，等于"源码或二进制 + 一个 INF"；包(Package)是一组模块的容器，必须有一个 DEC；平台(Platform)是特殊的包，必须有一个 DSC，可选一个 FDF。INF 描述单个模块自身：基本信息(BASE_NAME、FILE_GUID、MODULE_TYPE、VERSION_STRING、ENTRY_POINT)、依赖的包路径、源文件列表、消费/产生的库类、PCD、Protocol/PPI/GUID，以及 [Depex]。DEC 声明包对外的公共接口：[Includes] 公共头文件根目录、[LibraryClasses] 库类头文件、[Guids]/[Ppis]/[Protocols] 的 GUID 值、以及各类 PCD 的声明(默认值、数据类型、Token 号)。DSC 描述"怎么编"：[Defines] 设输出目录/架构/BUILD_TARGETS，[Components] 列出要编译的模块，[LibraryClasses] 为每个库类挑选具体库实例，[Pcds*] 段配置 PCD 的类型和值。FDF 只在需要生成 flash 镜像时才需要，描述 FD/FV 布局。build 工具解析 DSC + 各 DEC + 各 INF，生成一个顶层 makefile 以及每个模块各自的 makefile 和 AutoGen.c/AutoGen.h。注意一次 build 只有 active platform 的那个 DSC 生效。

Q: MODULE_TYPE 都有哪些？我该怎么给自己的模块选？入口函数又是怎么告诉构建系统的？
A: 常见类型有 SEC、PEI_CORE、PEIM、DXE_CORE、DXE_DRIVER、DXE_RUNTIME_DRIVER、DXE_SMM_DRIVER、DXE_SAL_DRIVER、UEFI_DRIVER、UEFI_APPLICATION、BASE。MODULE_TYPE 决定四件事：模块在哪个阶段被派发(PEIM 在 PEI 阶段，DXE_DRIVER/UEFI_DRIVER 在 DXE 阶段)、生成的 .efi 里带哪些 section(PEIM/DXE_DRIVER 可以有 depex section，UEFI_DRIVER 可以有 .ui/.ver section)、入口点和构造函数的原型、以及哪些库实例可以链给它(库实例的 INF 会声明自己支持哪些模块类型)。选型经验：跑在 PEI 阶段用 PEIM；只在 Boot Services 环境里活的用 DXE_DRIVER(ExitBootServices 时销毁)；要在 ExitBootServices 之后继续提供服务的用 DXE_RUNTIME_DRIVER；遵循 UEFI Driver Model 的设备驱动用 UEFI_DRIVER(返回 EFI_SUCCESS 就常驻，返回错误会被卸载)；Shell 下跑的工具用 UEFI_APPLICATION(退出即卸载)。入口点写在 INF 的 [Defines] 段 ENTRY_POINT = XxxEntryPoint，同时必须在 [LibraryClasses] 里链上对应的入口点库(UefiDriverEntryPoint / UefiApplicationEntryPoint / PeimEntryPoint)；真正的 _ModuleEntryPoint 由 AutoGen 生成，它先调用所有库实例的构造函数，再进你写的入口函数。目录命名惯例是 XxxPei / XxxDxe / XxxRuntimeDxe / XxxLib。

Q: 库类(Library Class)和库实例(Library Instance)到底是什么关系？为什么 DSC 里非要写一行映射？
A: 库类只是一组 API 声明，体现为放在 <Package>/Include/Library/XxxLib.h 里的头文件；库实例才是这组 API 的具体实现。同一个库类可以有多个实例，针对不同平台、不同阶段(SEC/PEI/DXE)、不同的性能与体积取舍——比如 DebugLib 就有 BaseDebugLibNull(空实现)、BaseDebugLibSerialPort、UefiDebugLibConOut、UefiDebugLibStdErr、PeiDxeDebugLibReportStatusCode；BaseMemoryLib 有通用版和用寄存器优化的 BaseMemoryLibOptDxe/OptPei。模块 INF 只写"我要用哪个库类"，不关心谁实现；由平台 DSC 的 [LibraryClasses] 段写 `库类名|库实例INF路径` 完成绑定。绑定可以分层覆盖：[LibraryClasses] 是全局默认，[LibraryClasses.IA32]/[LibraryClasses.common.UEFI_DRIVER] 按架构或模块类型覆盖，还可以在 [Components] 里对单个模块用 `Module.inf { <LibraryClasses> PcdLib|MdePkg/Library/DxePcdLib/DxePcdLib.inf }` 单独覆盖。库实例自己的 INF 必须在 [Defines] 写 LIBRARY_CLASS = 类名|支持的模块类型列表，可选写 CONSTRUCTOR/DESTRUCTOR：BASE 类型构造函数无参数(因此想链接到任意驱动类型就得用 BASE)，PEIM/PEI_CORE 类型收 (FileHandle, PeiServices)，DXE/UEFI 类型收 (ImageHandle, SystemTable)；析构函数由 ExitDriver() 调用，原型与构造函数相同。开发初期建议先用不带优化的通用实例降低风险，功能跑通后再换性能/体积优化版本。

Q: PCD 有几种类型？在 DEC / DSC / INF / C 代码里分别怎么写？什么时候必须用 FixedPcd？
A: 五种：PcdsFeatureFlag(BOOLEAN 开关，用来替代编译宏)、PcdsFixedAtBuild(编译期定值，存在 PE 镜像的代码段)、PcdsPatchableInModule(编译期定值但存在数据段，二进制镜像里可以打补丁改)、PcdsDynamic 与 PcdsDynamicEx(运行期由一个模块赋值、其他模块读取，PcdPeim 和 PcdDxe 各维护一份 PCD 数据库；若绑定到 UEFI 变量则在 DSC 里写成 [PcdsDynamicHii]，格式是 `PcdName|L"变量名"|变量GUID|偏移|默认值`)。写法：DEC 按类型分段声明 `TokenSpaceGuid.PcdName|默认值|数据类型|Token号`，支持多类型的 PCD 要在每个支持的类型段里都声明；DSC 按 [PcdsFeatureFlag]/[PcdsFixedAtBuild]/[PcdsPatchableInModule]/[PcdsDynamicDefault]/[PcdsDynamicHii] 段配置最终类型和值，DSC 里一个 PCD 只能定成一种类型，Dynamic 类型必须在 DSC 里全局配置且不能被单个驱动覆盖；INF 按用法写进 [FeaturePcd]/[FixedPcd]/[PatchPcd]/[Pcd] 段，同时 [Packages] 必须同时列出声明该 PCD 的包和 MdePkg(因为 PcdLib 在 MdePkg 里)。C 代码里 #include <Library/PcdLib.h>，然后用 PcdGetXX/PcdSetXX(所有类型通用)、FeaturePcdGet(仅 FeatureFlag)、FixedPcdGetXX、PatchPcdGetXX/PatchPcdSetXX。只有当 PCD 值要当编译期常量使用时才必须用 FixedPcd，典型是 `UINT8 MySampleArray[FixedPcdGet16(PcdArrayLength)]`；库实例里应尽量避免 FixedPcd，因为同一个库会被链接进不同模块而取到不同值。INF 里推荐统一写通用的 [Pcd] 段，把类型选择权留给平台集成者；同一个模块里也不要用两个同名但不同 TokenSpace 的 PCD。

Q: [Depex] 是干什么用的？为什么我 INF 里写了 TRUE，驱动还是没在我期望的时机跑起来？
A: Depex(依赖表达式)描述模块入口点被派发执行所需满足的条件，由一组 Protocol/PPI/GUID 的 CName 加 AND、OR、NOT、TRUE、FALSE 组成，写在 INF 的 [Depex] 段，用来决定 PEIM 和 DXE 模块的派发顺序，例如 `[Depex] gEfiSimpleTextOutProtocolGuid AND gEfiHiiDatabaseProtocolGuid AND gEfiVariableArchProtocolGuid`。两个最容易踩的坑：一是 DXE 驱动会继承它所链接的全部库实例的 Depex，最终 PE32+ 镜像里的依赖表达式是 INF 里写的和所有库实例的 Depex 逻辑与(AND)的结果——所以你写 TRUE 也可能因为继承而变成非 TRUE，而库实例是在 DSC 里选的，改 DSC 就会改变最终 Depex；二是被 apriori 文件覆盖的驱动，其 Depex 会被完全忽略，由 apriori 强制指定执行顺序。规则上：PEIM、DXE_DRIVER、DXE_RUNTIME_DRIVER、DXE_SAL_DRIVER、DXE_SMM_DRIVER 必须有 [Depex] 段(除非在 [Binaries] 里用 PEI_DEPEX/DXE_DEPEX/SMM_DEPEX 指定)；SEC、UEFI_APPLICATION、UEFI_DRIVER、PEI_CORE、DXE_CORE、SMM_CORE、HOST_APPLICATION 不允许有 [Depex]，并且它们所链接的库的 [Depex] 也一律被忽略；库模块的 [Depex] 可选，但 BASE 类型的库不允许写通用 [Depex]，只能写带模块类型修饰的如 [Depex.common.PEIM]。段名格式是 Depex[.<Arch>[.<ModuleType>]]，通用段和架构段不能混用。另外，当依赖恰好等于全部架构协议时，build 工具会直接把 depex section 从镜像里删掉。

Q: 怎么只编译我自己写的那一个模块？build 命令参数怎么写？产物和 AutoGen 文件在哪？
A: 先把模块 INF 的相对路径(从 workspace 根算起，包含包目录)加进某个 DSC 的 [Components] 段——需要限定架构就放进 [Components.IA32] 这类段，架构必须在 [Defines] 的 SUPPORTED_ARCHITECTURES 列表里。然后执行 `build -p <Package>.dsc -m <Module>.inf -a <ARCH> -b <TARGET> -t <TOOLTAG>`：-p 指定平台 DSC(不加 -m 就编该 DSC 里所有模块)，-m 指定单个模块(该模块必须已在这个 DSC 的 [Components] 里)，-a 指定架构(IA32/X64/EBC 等)，-b 指定 DEBUG 或 RELEASE，-t 指定 Conf/tools_def.txt 里定义的工具链 tag(如 MYTOOLS)。命令行不写的项取 Conf/target.txt 里的默认值；-p/-m 写多次是叠加，-a/-b/-t 写多次会依次串行编译。完整例子：`build -p MdeModulePkg/MdeModulePkg.dsc -m MdeModulePkg/Application/HelloWorld/HelloWorld.inf -a IA32 -b DEBUG -t MYTOOLS`，产物在 $(WORKSPACE)/Build/MdeModulePkg/DEBUG_MYTOOLS/IA32/MdeModulePkg/Application/HelloWorld/HelloWorld/ 下，其中 .efi、中间文件、AutoGen.h、AutoGen.c、Module.map 在 DEBUG 子目录，.lib 在 OUTPUT 子目录。AutoGen.c/.h 是 build 工具按 INF 信息为每个模块自动生成的，包含该模块用到的 GUID/Protocol/PPI/PCD 定义和入口点包装(先调所有库构造函数再进模块入口)；Module.map 由编译器生成，列出所有函数及其相对地址，配合模块运行时的加载基址就能把崩溃地址还原成函数名。编译选项有四级覆盖：改 tools_def.txt(影响全 workspace)、模块 INF 的 [BuildOptions]、DSC 的 [BuildOptions]、DSC 里针对单个模块的 `Module.inf { <BuildOptions> ... }`，其中 `=` 是追加、`==` 是整体替换，推荐只改后两种。

Q: 新手最常撞上的那几个编译/链接报错，分别是什么原因、怎么修？
A: 一、`error 4000: Value of Guid [gXxxGuid] is not found under [Guids] section in MdePkg.dec` —— 模块 INF 的 [Packages] 段少了声明该 GUID/PPI/Protocol/LibraryClass/PCD 的那个包的 DEC 文件，把对应的 .dec 路径补进去(路径从 workspace 根算，不是从模块目录算)。二、`error LNK2001: unresolved external symbol _gXxxGuid` —— INF 里少了对应的 [Guids]/[Ppis]/[Protocols] 条目，把那个 CName 补上。三、`error LNK2001: unresolved external symbol _LibraryFunctionName` —— INF 的 [LibraryClasses] 段少写了包含这个函数的库类，导致库实例没被链接进来。四、`error 4000: Instance of library class [XxxLib] is not found consumed by module [...]` —— DSC 的 [LibraryClasses] 段缺少这个库类到库实例的映射；如果模块其实并不需要它，正确做法是把这个库类从模块 INF 里删掉。五、`error 0010: File name case mismatch` —— DSC 或 INF 里写的文件路径大小写和文件系统里不一致(比如 Helloworld 对 HelloWorld)，所有元数据文件里的文件名和大小写必须与磁盘完全一致，并且路径分隔符要用 UNIX 风格的 "/" 而不是 "\"。六、`warning C4013: 'FeaturePcdGet' undefined; assuming extern returning int` —— 源码里忘了 #include <Library/PcdLib.h>，只要用 PCD 就必须包含这个头文件。

Q: 我想在代码里打印调试信息，DEBUG/ASSERT 要怎么配置才能真的输出？除了打印还有什么调试手段？
A: 四步缺一不可：(1) 用 DEBUG 目标编译，即 `build -b DEBUG` 或把 Conf/target.txt 里改成 TARGET = DEBUG，DEBUG 与 RELEASE 对应完全不同的编译选项；(2) 在 DSC 的 [LibraryClasses] 里给 DebugLib 选一个真正会输出的实例——BaseDebugLibNull 是空实现，什么都不会打，串口用 BaseDebugLibSerialPort，控制台用 UefiDebugLibConOut，标准错误输出用 UefiDebugLibStdErr，走 Status Code 上报用 PeiDxeDebugLibReportStatusCode；(3) 配好 DebugLib 消费的两个 PCD——PcdDebugPropertyMask 是 print/assert 能力的总开关，同时决定 ASSERT 宏是走 CpuDeadLoop 还是 BreakPoint；PcdDebugPrintErrorLevel 是打印等级掩码，DEBUG() 里的 ErrorLevel 与它按位与结果为 0 就会被过滤掉(源码里就是 `if ((ErrorLevel & PcdGet32 (PcdDebugPrintErrorLevel)) == 0) return;`)；(4) 需要时调编译选项，MSFT 工具链加 /Od 关闭优化避免指令重排导致单步乱跳，加 /FAsc 生成源码+汇编对照的 .cod 文件，写在 DSC 的 [BuildOptions] 或 [Components] 里针对单个模块加。另外两个常用手段：用 CpuDeadLoop() 把执行流卡死，快速确认代码有没有跑到这里；用模块的 map 文件配合运行时加载基址，把崩溃地址反算成具体函数。注意 Driver Binding 的 Supported/Start/Stop 里不允许使用控制台 I/O 协议，但可以用 DEBUG() 和 ASSERT() 宏。

Q: 写一个遵循 UEFI Driver Model 的驱动，Supported/Start/Stop 分别该做什么？Driver Binding 协议怎么装上去？
A: Supported() 只做一次快速检查，判断本驱动能不能管理这个控制器，并且绝对不能修改控制器状态——因为该控制器可能已经被别的驱动管着；如果控制器已被占用或被独占，必须返回错误。所有初始化或修改动作只能放在 Start() 里，不要因为"既然支持就顺手初始化"而写进 Supported()。Start() 才真正绑定：打开需要的父协议(通常用 EFI_OPEN_PROTOCOL_BY_DRIVER)、分配私有上下文结构、把自己产生的协议装到控制器句柄上(设备驱动)或创建带 DevicePath 的子句柄(总线驱动，比如 PCI 总线驱动给子设备装 EFI_DEVICE_PATH_PROTOCOL + EFI_PCI_IO_PROTOCOL)。Stop() 做 Start() 的逆操作：卸载装上去的协议、关闭打开过的协议、释放 Start() 里分配的资源。EFI_DRIVER_BINDING_PROTOCOL 除三个函数指针外还有 Version、ImageHandle、DriverBindingHandle 三个字段：Version 必须自己填，0x0~0x0F 和 0xFFFFFFF0~0xFFFFFFFF 保留给 OEM 驱动，IHV 用 0x10~0xFFFFFFEF，Version 值越高 ConnectController() 越先调用其 Supported()，每发布一个新版本都应递增；ImageHandle 和 DriverBindingHandle 一般初始化为 NULL，交给库函数自动填。安装在驱动入口点完成：可以直接调 gBS->InstallMultipleProtocolInterfaces()，但更推荐用 UefiLib 的 EfiLibInstallDriverBinding()、EfiLibInstallDriverBindingComponentName2()、EfiLibInstallAllDriverProtocols()、EfiLibInstallAllDriverProtocols2()。Driver Binding 装在驱动的 image handle 上；如果一个驱动产生多个 Driver Binding 实例，额外的实例必须装到新句柄上。安装过程中任何一步失败都应让整个驱动失败并返回 EFI_ABORTED 之类的错误；实现了 Unload() 的话，入口点里装的协议必须在 Unload() 里全部卸掉——Unload() 本身可选，但"装了就必须卸"不可选。

Q: 拿一个 Protocol 到底该用 LocateProtocol、LocateHandleBuffer 还是 OpenProtocol？OpenProtocol 的 Attributes 怎么选？
A: LocateProtocol() 只返回句柄数据库里第一个该协议实例，适合全系统最多只有一份的"服务型"协议，如 EFI_DECOMPRESS_PROTOCOL、EFI_ACPI_TABLE_PROTOCOL、EFI_HII_DATABASE_PROTOCOL、EFI_HII_STRING_PROTOCOL、EFI_FORM_BROWSER2_PROTOCOL、EFI_UNICODE_COLLATION_PROTOCOL 等。LocateHandleBuffer() 按 AllHandles 或 ByProtocol 一次取回一组句柄，返回的数组是内核用 AllocatePool 分配的，用完必须 FreePool，否则内存泄漏(ByRegisterNotify 这种搜索方式不建议在驱动里用)。OpenProtocol()/CloseProtocol() 才是驱动获取和释放协议接口的正规方式，它会把"谁在用(AgentHandle/ControllerHandle)、为什么用(Attributes)"记录进内核，可以用 Shell 的 openinfo、dh、connect、disconnect、reconnect、drivers、devices、devtree 命令检查用法是否正确；驱动调用时 AgentHandle 一般传 This->DriverBindingHandle。Attributes 的选法：EFI_OPEN_PROTOCOL_TEST_PROTOCOL 只测试协议在不在，不返回接口也不需要 Close，典型用在 Supported()；EFI_OPEN_PROTOCOL_GET_PROTOCOL 取接口但不独占、也不需要 Close，风险是协议被卸载时不会通知你，可能拿到失效指针，只在 BY_DRIVER 已被别人占用、且你能通过中间层被间接通知时才用它(EDK II 里 FAT 驱动跨过 DiskIo 去用 BlockIo 就是这种情况)；EFI_OPEN_PROTOCOL_BY_DRIVER 是驱动的首选，取接口并标记独占，别的驱动想用必须先让你 Stop()，用完必须在 Stop() 里 CloseProtocol()——CloseProtocol 的参数就是 OpenProtocol 去掉 Interface 和 Attributes；BY_DRIVER|EXCLUSIVE 会把正在使用该协议的其他驱动踢掉，很少用(DebugPort 驱动抢串口是个例子)，危险且可能导致系统失去唯一控制台；EFI_OPEN_PROTOCOL_BY_CHILD_CONTROLLER 供总线驱动使用，为每个子控制器代打开父设备的 I/O 抽象，让内核能追踪父子关系；EFI_OPEN_PROTOCOL_BY_HANDLE_PROTOCOL 只为兼容旧版 EFI 规范保留，驱动不要用。另外，装/卸协议时优先用 InstallMultipleProtocolInterfaces()/UninstallMultipleProtocolInterfaces()，它们出错会自动回滚到调用前状态、能防止重复的 Device Path、错误检查更严格、生成的代码也更小；同一个句柄上不允许装两个同 GUID 的协议实例，第一个协议装上去会自动创建句柄，最后一个协议卸掉会自动销毁句柄。

Q: 我想给 edk2 上游提一个补丁，完整的贡献流程是什么样的？
A: 官方把上手过程分成四步：一次性的工具安装、一次性的 workspace 搭建、每次改动都要做的开发与测试、每次改动都要做的代码评审与 CI。贡献者的具体操作是：(1) 从 origin/master 拉一个 topic 分支 `git checkout -b <new-dev-branch> origin/master`；(2) 在工作树里改代码；(3) 把改动拆成互相独立、不破坏 git bisect 的多个提交(`git add -u` 暂存所有修改，`git add <file>` 加新文件，`git add -p` 交互式分块暂存)；(4) 按 Commit Message Format 写提交信息，`git commit -s` 可自动追加 Signed-off-by；(5) 用 `python BaseTools/Scripts/PatchCheck.py -<N>` 检查最近 N 个提交的格式，强烈建议每提交一次就跑一次，这样有问题可以直接 amend；(6) `git fetch origin` 拉最新(注意它更新的是 origin/master 而不是本地 master)；(7) `git rebase origin/master` 变基到主线；(8) 跑 Uncrustify 自动格式化，本地 CI 的格式检查不过就无法合入；(9) 用 Stuart 在本地跑 CI，它既能编译也能跑编译之外的检查插件，跑的是和 PR 上一模一样的检查，比等服务器 CI 快得多；(10) 推到自己 fork 的分支：`git remote add <developer-id> https://github.com/<developer-id>/edk2.git` 然后 `git push <developer-id> <new-integration-branch>`；(11) 在 edk2 仓库建从该分支到 master 的 PR，描述里要带 `Fixes <issue url>` 才能自动关联 GitHub issue，如果只是想借 CI 跑一遍就建 draft PR；(12) 按评审意见改，单个提交用 `git commit --amend`，多个提交用 `git rebase -i origin/master`，然后强推更新 PR。默认情况下你可能无法在 PR 上留评论、也无法被加为 reviewer，需要发邮件到 devel@edk2.groups.io 申请加入 EDK II Collaborators。重大设计变更或架构提案建议先走 RFC 流程收集社区意见，这里描述的流程是针对代码贡献的。

Q: commit message 到底该怎么写？签名行有什么讲究？
A: 标准格式是「`Pkg-Module: Brief-single-line-summary` + 空行 + 正文 + 空行 + 签名」。细节规则：标题行 `Pkg-Module: 摘要` 整体长度要小于 72 个字符；CVE 修复必须在摘要后追加 CVE 号，格式为 `Pkg-Module: Summary (CVE-Year-Number)`，此时总长小于 92 字符；作为分隔的空行必须是不含任何空白字符的纯空行；正文每行尽量小于 76 字符，可以写上已验证的测试项；整条 log 只允许使用标准 ASCII 字符。跨包提交有专门写法：改动的包少于 4 个时写成 `Package,Package,Package/Module: 摘要`(包名用逗号分隔)，大于等于 4 个包时统一写 `Global: 摘要`，两种情况都要在签名之前加一行 `Continuous-integration-options: PatchCheck.ignore-multi-package`。签名规则：所有签名放在 log 末尾，正文之后空一行开始，一行一个签名，新签名追加到列表最后；作者用 `Signed-off-by: Your Name <your.email@host.com>`，必须是真实姓名和邮箱，名字里含逗号要加引号写成 `"Last, First" <mail>`；如果代码是从可信来源拿来转发的，也要加上自己的 Signed-off-by，表示你确认这份代码社区可用；评审者用 `Reviewed-by:`，如果希望作者改完后再复审一遍，就先不要给出 Reviewed-by。签名格式必须严格遵守，以便自动化工具在需要时剥离这些行。转为 PR 流程之后，`Cc`、`Reviewed-by`、`Acked-by`、`Tested-by` 这些 tag 在 commit message 里已不再required；`git revert` 自动生成的 `Revert "Pkg-Module: ..."` 标题行也是允许的。

Q: 一个改动该拆成几个 commit？拆分标准是什么？
A: 核心原则有两条：每个 commit 只修一个问题或只加一个特性；每个 commit 单独拿出来都要能编译、能在代码树里正常工作——后者是为了不破坏 `git bisect` 这个定位问题引入点的强力工具。大的改动要拆成若干逻辑小块，每块都自洽。该分开提的例子：同时提交一个库类(或 PPI、Protocol)的接口定义和它的实现时，接口可以先单独一个 commit，因为接口与实现在逻辑上是分离的；同一个文件或模块里的多处修复，如果彼此足够独立，也应该考虑分开。不该再细分的例子：在一个文件里改了 5 个注释拼写错误，不需要拆成 5 个 commit；一个全新的驱动或库实现，绝大多数情况下就是一个 commit。遇到 bisect 冲突时的处理办法：先看看调整提交顺序能不能让每个 commit 都保持可编译可运行；在补丁系列中间加临时代码、在系列末尾再删掉，是被明确接受的做法。测试责任上，开发者只需保证自己惯用的工具链能编过，条件允许时最好 Microsoft 和 GCC 两套工具链都试一下。另外，提交拆分得合不合理本身就属于代码评审的内容，评审者应当就此给出反馈。

Q: Uncrustify 是什么？怎么在本地把代码格式化成 CI 认可的样子？
A: Uncrustify 是一个源码美化工具，edk2 用它把 C 代码自动格式化成符合《EDK II C Coding Standards Specification》的形式，并在 CI 里以 UncrustifyCheck 插件强制检查，格式不合规的 PR 无法合入。注意必须用 tianocore 自己 fork 的版本(https://github.com/tianocore/uncrustify)，因为有些 EDK II 特有的格式细节没法只靠配置控制，同时必须搭配仓库里的 `.pytool/Plugin/UncrustifyCheck/uncrustify.cfg` 配置文件。推荐流程：克隆 edk2 → 用 `stuart_update` 把 Uncrustify 拉进 workspace(落到 `.pytool/Plugin/UncrustifyCheck/tianocore-uncrustify-release_extdep`，内含 Linux 和 Windows 两个可执行文件) → 装 VS Code 的 Uncrustify 扩展(id: zachflower.uncrustify)并在 settings.json 里配好 `uncrustify.configPath.windows` 与 `uncrustify.executablePath.windows`，之后 Ctrl+Shift+P → Format Document 一键格式化 → 本地跑 `stuart_ci_build -c .pytool/CISettings.py -p MdeModulePkg` 验证 UncrustifyCheck 通过 → 再推分支建 PR。命令行手动跑的推荐写法是把文件列表通过 stdin 喂进去，例如 `git ls-files DynamicTablesPkg*.c DynamicTablesPkg*.h | ./.pytool/Plugin/UncrustifyCheck/tianocore-uncrustify-release_extdep/Linux-x86/uncrustify -c ./.pytool/Plugin/UncrustifyCheck/uncrustify.cfg -F - --replace --no-backup --if-changed`，其中 `-c` 指定配置文件、`-F -` 表示从 stdin 逐行读文件名、`--replace --no-backup` 原地改写便于用 git diff 看效果、`--if-changed` 只在确有变化时输出。CI 上失败时的排查路径是：GitHub PR 里点失败流水线的 Details → View more details on Azure Pipelines → 找到失败的 job 和 step → 点顶部的测试通过率 → 找到 `Check file coding standard compliance in ...` 这条失败测试 → Attachments → `Standard_Error_Output.log`，里面是需要改成什么样的完整 diff；如果 diff 看起来是空的，先检查文件行尾是不是 CRLF，新增文件尤其容易踩这个坑。

Q: PR 提上去后 CI 会跑哪些检查？谁来 review？最后怎么合进 master？
A: edk2 的 CI 建立在 GitHub + Azure Pipelines + Mergify + edk2-pytool 之上，PR 阶段跑三个预提交作业(PatchCheck、Windows/VS、Linux/GCC)，目标是十分钟内全部跑完，合入后还有两个后提交作业，主线状态显示在 edk2/master 的 Readme.md 顶部。预提交的检查插件包括 PatchCheck(提交信息与补丁格式)、CharEncodingCheck(字符编码)、CompilerPlugin(编译)、DependencyCheck(包依赖规则)、DscCompleteCheck(模块是否都进了 DSC)、GuidCheck(GUID 重复/冲突)、LibraryClassCheck(库类声明)、SpellCheck(拼写)，以及 UncrustifyCheck(代码格式)。常见失败与处理：检测到 merge conflict 就在本地把分支 rebase 到 edk2/master、解冲突、amend 相关提交后强推，强推会自动重跑检查；PatchCheck.py 不过就按报错改提交信息再强推；Windows/Ubuntu 检查失败则顺着 PR 里的 Azure Pipelines 链接看测试结果；实在搞不定就在 PR 里留言求助。评审方面：被改动的每个代码区域在仓库根目录 `Maintainers.txt` 里都登记了 reviewer 和 maintainer，可以用 `BaseTools/Scripts/GetMaintainer.py` 自动算出该加谁；你自己是 maintainer 就自己加 reviewer，否则由 maintainer 帮你加。所有会话必须解决 PR 才能完成，规则是：作者处理完反馈后可以自行 resolve，但要留言说明怎么解决的，且必须与提出者达成一致才算数；评审者若希望自己的意见一定被处理，应该用「文件评论」而不是泛泛的 PR 评论，因为只有代码文件里的评论必须被 resolve 之后 PR 才能完成。合入规则：每个被改动的代码区域至少有一位 reviewer 批准后，maintainer 给 PR 打上 `push` 标签，所有状态检查通过且无冲突时 Mergify 会自动以严格 rebase 的方式把补丁并入 master；禁止 squash，每个 commit 都必须能独立提交到 master。

Q: EDK II 的命名规范有哪些硬性要求？
A: 标识符(文件名、函数名、变量名、枚举成员、结构体成员)统一用 `EachWordIsDistinctEvenAcronymsLikeAcpi` 这种每个单词首字母大写的形式，必须大小写混合，全大写或全小写都不允许，因为复合词会分不开；缩略词不要整个大写，`MyPciAddress` 比 `MyPCIAddress` 好读，和数字混排时尤其明显(`My870PCIBus0BDF` 就很难读)，但注释和文档里的缩略词要按英文习惯大写。功能宏、`#define`、`typedef` 用 `EACH_WORD_IS_DISTINCT_EVEN_ACRONYMS_LIKE_ACPI` 这种全大写加下划线分隔的形式，并且禁止用 `_t` 后缀表示类型。禁止匈牙利命名法，只有三个例外：文件作用域及以上的变量必须加前缀，全局变量用 `g`(如 `gThisIsAGlobalVariableName`)、模块变量用 `m`(如 `mThisIsAModuleVariableName`)，这条无一例外；指针变量可以可选地加 `p` 前缀。其他约束：名字长度不限但建议 10~30 字符，且不能依赖超过 31 个字符的区分度；文件名不能以数字开头，每个头文件名必须唯一；名字要视觉上易区分，长名字之间不要只差一两个字符，避免混淆 0 与 O、1 与 l；禁止使用 C 关键字或标准头文件中已声明的符号作为内部符号，外部符号名不得以下划线开头；新建的全局实体(结构体、宏、define)不要再用 `EFI_` 前缀，`DXE_` 和 `PEI_` 前缀分别保留给 DXE 和 PEI 驱动，同时适用于两者时用 `DXE_`，仅在单个模块内部使用的结构体不需要特殊前缀；只能使用标准缩写和行业标准缩略词，任何非标准的缩写或缩略词都必须在使用它的文件的文件头注释里定义；禁止函数名或类型名重载。全局与模块变量本身也是「强烈不建议使用」的，全局变量只适合 GUID、Protocol、PPI 定义这类不可变对象，滥用会增大镜像体积甚至让变量落到 ROM 里；确实要用时，跨 TPL 访问的数据必须加锁保护。

Q: 排版和空白有哪些规定？
A: 总体规则：不允许出现 Tab 字符，所有缩进一律两个空格；单行不超过 120 列；所有行必须以 CRLF(0x0D 0x0A)结尾，文件末尾也必须是 CRLF；文件内只允许出现 ASCII 的 0x0A、0x0D 和 0x20~0x7E；新文件除 `#pragma pack(#)` 外不允许用 `#pragma`(移植进来的文件可保留原有 pragma，也可用 pragma 关掉大量重复告警)；每个新文件都必须以文件头注释块开头；头文件必须在所有其他指令、声明、定义之前写 `#pragma once`(工具生成或从外部项目直接拷入、改用 include guard 的文件除外)，C 头文件扩展名统一为 `.h`，`#include` 语句里不能出现绝对路径或含 `..` 的路径。纵向排版：用空行和注释把相关代码分组；一行只能有一条语句；条件和代码体不能写在同一行；一行只能有一个声明，`UINT8 MyData1, MyData2;` 是非法的；函数以及多行谓词表达式的左花括号 `{` 必须独占一行并与流程控制语句首字符对齐，其余情况下 `{` 跟在单行谓词的右括号之后；右花括号 `}` 总是位于函数体最后一行的行首并与该结构第一行对齐，例外是 `else {`、`else if () {` 和 `do-while` 可以与 `}` 共行；复杂谓词表达式的每个子表达式必须各占一行。横向排版：二元运算符前后必须有空格；一元运算符与其操作数之间不能有空格；逗号或分号之后若还有代码必须加空格；`(` 之前要有空格，但 `((` 和宏定义的 `(` 除外；`{` 若不独占一行，其前面要有空格；`.` 和 `->` 前后都不加空格；数组下标 `[` 之前不加空格；续行要与被续的那部分对齐，多行函数调用建议对齐到函数名之后一到两个缩进位。谓词表达式：不要依赖 C 的运算符优先级，一律显式加括号；BOOLEAN 不需要和 `TRUE`/`FALSE` 比较；指针必须显式与 `NULL` 比较；数值必须显式与另一个数值比较。

Q: 为什么不能用 int、char 这些标准 C 类型？该用什么？
A: 因为 UEFI 规范定义了一套通用数据类型来保证在不同编译器和不同处理器架构间的可移植性，所以 EDK II 明确规定只能使用 UEFI 数据类型，使用 `int`、`unsigned`、`char`、`void`、`long` 属于违反编码规范，任何自定义的抽象类型也必须由其他抽象类型或 EFI 通用类型构造出来。常用类型：`BOOLEAN`(1 字节，0 为 False、1 为 True，其他值未定义)、`INTN`/`UINTN`(本机宽度有符号/无符号整数，IA-32 上 4 字节、X64 上 8 字节)、`INT8`/`UINT8`/`INT16`/`UINT16`/`INT32`/`UINT32`/`INT64`/`UINT64`、`CHAR8`(1 字节字符)、`CHAR16`(2 字节字符，字符串默认按 UTF-16 存储)、`VOID`、`EFI_GUID`(128 位，默认 64 位边界对齐)、`EFI_STATUS`(实为 `UINTN`)、`EFI_HANDLE`/`EFI_EVENT`(实为 `VOID *`)、`EFI_LBA`(`UINT64`)、`EFI_TPL`(`UINTN`)；常量只用 `TRUE`、`FALSE`、`NULL`。修饰符：`IN`、`OUT`、`OPTIONAL`、`UNALIGNED` 只能用于修饰函数参数，绝不能出现在数据类型声明里；`CONST` 用于提示编译器优化和加强编译期类型检查，`VOLATILE` 用于禁止优化，凡是代表硬件设备的变量都应声明为 `VOLATILE`；`EFIAPI` 用来统一调用约定，所有 UEFI 定义的 API、所有变参函数、所有协议成员函数以及驱动对外暴露的公共函数都必须加 `EFIAPI`，否则跨模块调用时不同编译器的本机调用约定会对不上。此外：结构体必须写成 `typedef struct {...} TYPE;`，禁止 `struct {...} variable;` 这类直接声明，只有自引用或需要前向引用的结构体才允许带 name 标签；枚举必须 typedef，最后一个成员应是一个 Max 成员以便做边界检查和调试(如 `EnumMemberMax`)，也建议有一个最小成员，「原样使用」的常量优先用 enum 而不是 `const int`(enum 不用时不生成代码，还能做类型检查)，用于拼装其他值的常量(位域定义、掩码)才用宏；位域只能是 `INT32`、`signed INT32`、`UINT32` 或其 typedef，且位域的符号性、在存储单元内的分配顺序、存储单元的对齐都是编译器相关的，跨编译器代码不能依赖。

Q: 函数该怎么排版？文件头和函数头注释有什么格式要求？
A: 函数定义的排版是逐行规定死的：第一部分是 Doxygen 风格的函数头注释块；接下来可选地写存储类；然后单独一行写返回类型(没有返回值就写 `VOID`)；再单独一行写 `EFIAPI` 等修饰符；再一行是左对齐的函数名后跟一个左括号 `(`，这一行不允许出现任何参数；接下来每个参数各占一行、缩进两个空格，类型列和参数名列要对齐以便阅读，这一段里不允许写注释(参数说明一律放在函数头注释里)；右括号 `)` 单独一行并缩进两个空格；函数体的左右花括号各自独占一行并顶到第一列，函数体其余各行按两个空格的倍数缩进。无参数的函数必须写成 `(VOID)`，写空参数列表 `()` 是禁止的，此时右括号可以与函数名同行。参数必须带 `IN`/`OUT`/`IN OUT`/`OPTIONAL` 修饰符，建议 `IN` 参数在前、`OUT` 在后，传入后又被函数修改的缓冲区标 `IN OUT`；如果函数头注释里已提供了完整的 `@param[in,out]` 描述，`IN`/`OUT` 修饰符可以省略。函数原型与函数定义形式完全一致，只是参数列表的右括号后要加分号。文件作用域的数据定义必须是模块里的第一段代码，出现在其他位置是非法的，且不要给这些数据声明加注释(名字应当自解释，复杂类型的说明放到定义该类型的头文件里)。注释格式：每个文件必须以 `/** @file ... **/` 文件头块开头，内含简述、详细描述、`Copyright (c) 20XX, XXX. All rights reserved.<BR>`、`SPDX-License-Identifier: BSD-2-Clause-Patent`，以及 `@par Specification Reference:` 列出所依据的规范名称、版本和章节；每个新函数和功能宏都必须有紧挨定义之前的函数头注释块，写清简述、详细说明(算法、副作用等)、每个 `@param[in]`/`@param[out]`/`@param[in,out]` 的含义和每个 `@retval` 的含义。最常用的 Doxygen 命令是 `@file`、`@param[in,out]`、`@retval`、`@sa`、`@test`；C 风格文档块写成 `/** ... */`，C++ 风格用 `///`；注释默认写在被文档化元素之前，要写在成员之后则用 `///<` 形式。

Q: 流程控制语句、goto 和 ASSERT 有什么规定？注释有哪些禁忌？
A: 流程控制：`if`、`for`、`do`、`while` 的循环体必须是复合语句(带花括号)，即使是空循环体也要写成三行的空复合语句——左花括号在关键字行末，中间一行只有一个缩进正确的分号，右花括号与关键字同列，不过这种写法本身就不好读，应尽量避免。`if` 后跟一个空格再跟左括号，右括号后一个空格再跟左花括号，体内缩进两格，右花括号独占一行并与 `if` 对齐；`else` 可以写在 `if` 的右花括号同一行(`} else if (EXPR_2) {`)，也可以另起一行与右花括号对齐，`else` 与前后花括号之间都必须有一个空格，且 `else` 后面必须跟花括号。`switch` 的 `case` 缩进零个或一个缩进位、case 体再缩进一位，`switch` 的右花括号与 `switch` 的 `s` 同列；必须始终写 `default` 分支，并且 `default` 必须以 `break` 结尾(哪怕 `break` 就是右花括号前最后一句)；凡是有意让一个 `case` 落入下一个 `case`(即第二个及之后的 `case` 前没有 `break`)，都必须写一条说明性注释；同一模块内各文件的 case 缩进风格要保持一致，模块里已有文件用零缩进就跟着用零缩进。`goto` 原则上不应使用，几乎所有情况都能改写掉，一旦使用就要准备在评审时为它辩护；唯一合法的用途是错误退出，好处是把清理代码集中在一处、减少维护成本，标签要比它所标记的代码少缩进一级。ASSERT：`ASSERT` 系列宏(含 `ASSERT_EFI_ERROR`、`ASSERT_PROTOCOL_ALREADY_INSTALLED` 以及 `DebugLib.h` 里的所有 ASSERT 宏)只是开发和调试的辅助手段，绝不能用于错误处理——因为 `PcdDebugPropertyMask` 可以把 ASSERT 相关代码整个关掉，所以所有代码必须在 ASSERT 被禁用时仍能正常运行并合理恢复；断言只用来捕捉发布前就应修掉的编程错误，凡是程序员控制不了的参数和条件都必须用真正的代码去检查，同时也要设法把这类程序化错误处理的需求降到最低。注释禁忌：局部注释必须用 `//` 风格，注释块之前要有空行，注释缩进与代码一致，注释若只适用于紧随其后的一段代码就不要用空行隔开、若适用于多段则要空一行；注释要解释「为什么」而不是「怎么做」，把代码写干净往往比加更多注释更好；代码里不允许出现任何标记，包括 `BUGBUG`、你的名字、你的姓名缩写、`FIX_THIS`、`TEST` 之类，要跟踪 bug 请用 bug 系统，实在要标就用 Doxygen 的 `@bug` 或 `@todo`。另外，为压制静态分析器误报而做的「多余赋值」(如 `LocalIntegerVariable = 0;`、`LocalPointerVariable = NULL;`)必须逐个加注释说明，否则无法与真正有意义的初值赋值区分开。

Q: Driver Binding 的 Supported()、Start()、Stop() 三者职责边界怎么划分？
A: 三个服务构成 `EFI_DRIVER_BINDING_PROTOCOL`，原型分别是 `Supported(This, ControllerHandle, RemainingDevicePath OPTIONAL)`、`Start(This, ControllerHandle, RemainingDevicePath OPTIONAL)`、`Stop(This, ControllerHandle, NumberOfChildren, ChildHandleBuffer)`。Supported() 只做一次快速检查，回答「本驱动能不能管理这个控制器」，同时也要能识别出该控制器是否已被启动使用、或已被其他组件独占——这两种情况必须返回错误。Supported() 有一条硬性禁令：不得修改控制器状态，也不得触碰或改变任何硬件设备的状态，因为该控制器可能正被另一个驱动管理；在 Supported() 里顺手做初始化会显著拖慢驱动性能，还可能让设备、本驱动和其他驱动失去同步、行为异常且不可预测。Start() 才是真正的绑定动作，所有初始化和修改动作只能放在这里。Stop() 做的是 Start() 的严格逆操作：把驱动从控制器上断开、释放 Start() 里分配的全部资源，并且必须把相关句柄恢复到 Start() 被调用之前的状态。所有遵循 UEFI Driver Model 的驱动都必须实现 Stop()。三个服务都不允许使用控制台 I/O 协议，但可以用 DebugLib 的 `DEBUG()` 和 `ASSERT()` 宏往标准错误控制台输出信息，这些宏通常在驱动开发期启用、发布时关闭。设备驱动与总线驱动的关键区别就在这三个服务的行为上：设备驱动不产生任何子句柄、忽略 `RemainingDevicePath` 参数、从控制器句柄消费一个或多个 I/O 协议并在同一个句柄上产生一个或多个 I/O 协议；总线驱动则必须产生子句柄，并在每个子句柄上产生 I/O 协议。

Q: Supported() 具体该怎么写？各个返回码是什么含义？
A: 以 PCI 驱动为例的标准写法：先用 `OpenProtocol()` 以 `EFI_OPEN_PROTOCOL_BY_DRIVER` 属性打开 `ControllerHandle` 上的 PCI I/O Protocol(AgentHandle 传 `This->DriverBindingHandle`，ControllerHandle 传 `ControllerHandle`)，打不开就说明本驱动不支持该控制器，直接返回；打开成功后用 `PciIo->Pci.Read()` 从 PCI 配置头偏移 `PCI_VENDOR_ID_OFFSET`(0x00)和 `PCI_DEVICE_ID_OFFSET`(0x02)读出 VendorId 和 DeviceId，必要时还读 ClassCode，与本驱动支持的值比对，匹配则返回 `EFI_SUCCESS`，不匹配返回 `EFI_UNSUPPORTED`；无论走哪条路径，最后都必须用 `CloseProtocol()` 把打开的协议关掉(参数与 OpenProtocol 相同，去掉 Interface 和 Attributes 两项)。如果检查过程本身不需要调用该协议的服务，也可以直接用 `EFI_OPEN_PROTOCOL_TEST_PROTOCOL` 属性——这种模式不返回接口，因此也不需要 Close。返回码必须认真判断：`EFI_SUCCESS` 表示已把调用者加入该协议接口的打开列表；`EFI_UNSUPPORTED` 表示句柄不支持该协议；`EFI_ACCESS_DENIED` 表示当前环境无法满足所要求的属性；`EFI_ALREADY_STARTED` 表示打开列表里已存在一项 AgentHandle 相同且具备所需属性的记录——对设备驱动来说收到它意味着不该再去管这个控制器，但对总线驱动来说它只是表示自己已经连上了该控制器，可能完全正常，所以某些错误码对特定驱动而言根本不是错误。图形驱动这类还应先确认 `EFI_DEVICE_PATH_PROTOCOL` 和 `EFI_PCI_IO_PROTOCOL` 都存在，以确保传进来的句柄确实代表一个 PCI 设备。最后提醒一点：改 PCI 配置空间寄存器时要「读—改位—写」，不要直接写，否则会把同一寄存器里的其他位一并复位。

Q: Start() 里应该按什么顺序做事？
A: 典型顺序是：(1) 用 `OpenProtocol()` 以 `EFI_OPEN_PROTOCOL_BY_DRIVER` 打开要消费的 I/O 协议——正是这个属性在 UEFI Driver Model 里实现了资源冲突规避，它会先检查该协议是否已被其他驱动消费，只有没被消费时才成功，但这要求系统里所有驱动都遵守互操作规则才真正有效；总线驱动和混合驱动还要以同样属性打开 Device Path Protocol，设备驱动则不必打开 Device Path。(2) 用 `AllocatePool()`(或 `MemoryAllocationLib` 的 `AllocateZeroPool()`)分配并清零私有上下文结构，PCI 驱动通常还要在结构里留一个 `UINT64` 字段保存原始 PCI 属性。(3) 初始化适配器、分配资源、构造驱动自用的数据结构。(4) PCI 驱动必须调用 `PciIo->Attributes()`：先用 `EfiPciIoAttributeOperationGet` 取出并保存原始属性，再用 `EfiPciIoAttributeOperationSupported` 查出控制器支持哪些属性，最后用 `EfiPciIoAttributeOperationEnable` 打开配置头 Command 寄存器里的 I/O、内存和总线主控位——PCI 总线驱动默认不会替你使能 Command 寄存器，这是 Start() 的责任、也是 Stop() 恢复的责任；如果该控制器是能产生 64 位 DMA 地址的总线主控，还必须一并使能 `EFI_PCI_IO_ATTRIBUTE_DUAL_ADDRESS_CYCLE`，因为总线驱动默认假定所有 PCI 控制器只能产生 32 位 DMA 地址，漏报会导致在内存大于 4GB 的平台上被迫双缓冲、性能下降，甚至在只有 4GB 以上内存的平台上无法工作；`Attributes()` 调用失败时 Start() 必须返回错误。(5) 设备驱动把自己产生的 I/O 协议装到同一个控制器句柄上；总线驱动则为子设备创建子句柄，装上 `EFI_DEVICE_PATH_PROTOCOL`(子句柄代表物理设备时必须装，虚拟设备可不装)和子设备的 I/O 协议，并且每创建一个子句柄，都要以 `EFI_OPEN_PROTOCOL_BY_CHILD_CONTROLLER` 属性再打开一次父设备的 I/O 协议(Handle 传父控制器句柄、ControllerHandle 传子句柄)，把父子关系记录进句柄数据库，供 `DisconnectController()` 使用。(6) 处理 `RemainingDevicePath`：设备驱动直接忽略这个参数；总线驱动强烈建议解析它，非 NULL 时只创建它指定的那一个子设备，为 NULL 时才一次性创建全部剩余子句柄，这能显著提升平台启动速度；解析后发现要求的子设备本驱动不认识，应清理已分配的内存并返回 `EFI_UNSUPPORTED`。另外为了缩短启动时间，不要在 Start() 里做默认模式设置和清屏这类动作(以图形驱动为典型)，把模式选择交给 Boot Manager 统一做一次。中途任何一步失败都必须把前面已完成的动作全部回滚。

Q: Stop() 里要做什么？NumberOfChildren 和 ChildHandleBuffer 怎么用？
A: Stop() 必须让句柄数据库回到 Start() 调用之前的状态，顺序上基本是 Start() 的倒放：(1) 先卸载所有子句柄上的协议并销毁子句柄，子句柄当初以 `EFI_OPEN_PROTOCOL_BY_CHILD_CONTROLLER` 打开的父协议也要用 `CloseProtocol()` 关掉(此时 ControllerHandle 参数传的是子句柄)；(2) 卸载装在宿主控制器句柄上的所有协议；(3) 关闭 Start() 里打开的所有协议实例；(4) 恢复 Start() 里改动过的硬件状态，PCI 驱动要用 `PciIo->Attributes(PciIo, EfiPciIoAttributeOperationSet, Private->OriginalPciAttributes, NULL)` 把原始属性写回去，再 `CloseProtocol()` 关掉 PCI I/O；(5) 释放为本驱动分配的全部资源，用 `FreePool()` 释放私有上下文；(6) 必要时禁用适配器。拿回私有上下文的标准做法是：先用 `OpenProtocol()` 加 `EFI_OPEN_PROTOCOL_GET_PROTOCOL` 从 ControllerHandle 上取回自己在 Start() 里装上去的某个协议接口，取不到就返回 `EFI_UNSUPPORTED`，取到后用 `CR(Record, TYPE, Field, Signature)` 宏从这个协议指针反算出私有结构地址——`CR()` 在 DEBUG 版本会额外校验结构里的 Signature 字段，不匹配就 ASSERT 并停机，RELEASE 版本通常关掉这个校验；没有 Signature 字段的结构用 `BASE_CR()`。`NumberOfChildren` 和 `ChildHandleBuffer` 用于告诉驱动这次要停掉哪些子设备：总线驱动据此只销毁被点名的子句柄，`NumberOfChildren` 为 0 时表示要停的是控制器本身，设备驱动因为不产生子句柄，可以忽略这两个参数。还要注意一个隐患：卸载协议时 UEFI 内核会检查是否有其他驱动正在使用该协议，有的话会先调 `DisconnectController()` 尝试停掉它们；若 `DisconnectController()` 失败，内核会再调 `ConnectController()` 把句柄数据库恢复原状，这个重入过程在支持热插拔的总线上尤其容易出问题(丢失或错连指针、数据丢失、行为混乱甚至崩溃)，写热插拔设备驱动时必须把这种重入场景考虑进去。

Q: 什么时候一个驱动需要多个 Driver Binding 实例？写完怎么验证三个服务是对的？
A: 判断方法是把驱动消费的协议写成一个布尔表达式，再展开成「积之和」形式，每一个乘积项需要一个独立的 `EFI_DRIVER_BINDING_PROTOCOL` 实例。例如只消费 `Protocol A`、或消费 `(Protocol A AND Protocol B)`，都只有一个乘积项，一个实例就够；而 `(A AND (B OR C))` 展开成 `((A AND C) OR (B AND C))` 有两个乘积项，就需要两个 Driver Binding 实例，一个测 A 和 C、另一个测 B 和 C。每个实例的 Supported() 尝试打开它那个乘积项里的所有协议，任何一个失败则 Supported() 失败，全部成功才算支持；Start() 打开该乘积项里的所有协议，Stop() 再逐一关闭。多实例情况下所有实例都在驱动入口点一次性安装，第一个装在驱动的 image handle 上，其余必须装到新建的句柄上，各实例可以共用工作函数以减小驱动体积。`Version` 字段影响被调用的先后：`ConnectController()` 按五级优先级挑驱动——Context override(参数传入的有序句柄列表，通常只在 Shell 里调试新驱动时用)、Platform driver override、Driver family override、Bus specific driver override(让 PCI 卡自己 Option ROM 里的驱动优先管理该卡)、最后才是按 Driver Binding 的 `Version` 从高到低排序；排好序后逐个调 Supported()，通过就调 Start()，即使前面的驱动已连接成功，后面的驱动仍会得到机会，除非前面的驱动以 EXCLUSIVE 独占了父 I/O 协议。验证手段是 UEFI Shell：`load` 把驱动加载进内存、`dh` 确认 Driver Binding 已正确装入句柄数据库、`connect` 触发 Supported() 和 Start()、`disconnect` 触发 Stop()、`reconnect` 一次跑完三个服务，再配合 `drivers`、`devices`、`devtree` 查看驱动与设备的关系，用 `openinfo` 查看每个协议被谁以什么属性打开(这是核对 OpenProtocol/CloseProtocol 是否成对、属性用得对不对的最直接办法)，`unload` 用来测 Unload() 路径。完整验证还需要启动 UEFI 操作系统并运行 UEFI SCT(Self Certification Test)。
R: edk2-UefiDriverWritersGuide/6_uefi_driver_categories/61_device_drivers/616_device_driver_protocol_management.md 6.1.6 (sum-of-products rule); edk2-UefiDriverWritersGuide/9_driver_binding_protocol/91_driver_binding_protocol_implementations.md 9.1; edk2-UefiDriverWritersGuide/9_driver_binding_protocol/93_testing_driver_binding_protocol.md 9.3 Testing Driver Binding Protocol; edk2-UefiDriverWritersGuide/3_foundation/314_uefi_driver_model_connection_process/3141_connectcontroller.md 3.14.1 ConnectController()

Q: UEFI/PI 固件从上电到把控制权交给 OS，启动流程分哪几个阶段？每个阶段各干什么？
A: PI 架构把启动分为 SEC→PEI→DXE→BDS→TSL→RT（另有 AL）六个阶段。SEC(Security) 是第一个阶段：处理所有平台复位事件、利用 CPU 内部资源（如 Cache as RAM）建立临时内存、充当系统信任根(Root of Trust)、把 handoff 信息（可选含 SEC Platform Information PPI、处理器健康状态）传给 PEI Core。PEI(Pre-EFI Initialization) 阶段代码要尽可能薄：初始化永久内存、派发 PEIM、用 HOB(Hand-Off Block) 描述内存和固件卷(Firmware Volume)位置、最后把控制权交给 DXE；它还负责危机恢复和 S3 唤醒，所以代码路径必须最短。DXE(Driver Execution Environment) 是系统初始化的主体：DXE Core(Foundation) 产生 Boot Services / Runtime Services / DXE Services，DXE Dispatcher 按依赖顺序发现并执行 DXE 驱动，驱动们初始化处理器/芯片组/平台并提供控制台与启动设备的软件抽象；DXE 在 OS 成功启动时终止，DXE Core 自身代码不允许残留到 OS runtime。BDS(Boot Device Selection) 在所有依赖满足的 DXE 驱动派发完后，由 DXE Foundation 交给 BDS Architectural Protocol：初始化控制台设备、加载设备驱动、按 UEFI Boot Manager 的启动策略尝试启动各个启动项；若无法推进会重新调用 DXE Dispatcher。TSL(Transient System Load) 是 OS loader 作为 EFI application 运行的阶段。RT(Run Time)：OS 接管后只剩有限的 Runtime Services——环境变量读写、RTC 实时钟、单调计数、capsule 固件更新；OS 可用虚拟地址调用（SetVirtualAddressMap 是单程门），因此 runtime 代码通常隔离在 runtime driver 里。AL(After Life)：OS 崩溃后固件可做恢复/补救，UEFI/PI 不规定此阶段行为。
R: tianocore-wiki.github.io/development/design-architecture/pi_boot_flow.md（SEC/PEI/DXE/BDS/TSL/RT/AL 各段）; PI_Spec_1_8_A_final_2024.03.05.pdf Volume I 章节 I-6.2 Pre-EFI Initialization (PEI) Phase、Volume II 章节 II-1 Introduction / II-2 Overview（DXE）

Q: PEI 阶段还没有 DXE 的 Boot Services，PEIM 之间怎么互相调用？PPI 和 HOB 分别是什么？
A: PEI 用两套核心机制替代 DXE 的 Protocol/服务表。PPI(PEIM-to-PEIM Interface) 是 PEIM 之间互相暴露服务的接口，角色相当于 DXE 阶段的 Protocol：一个 PEIM 通过 PEI Services 的 InstallPpi() 把 "GUID + 接口结构体" 注册进 PEI Foundation，其他 PEIM 用 LocatePpi() 按 GUID 查找，NotifyPpi() 可在目标 PPI 安装时得到回调通知；PEIM 的 INF [Depex] 段里写的依赖也是 PPI GUID，PEI Dispatcher 据此决定派发顺序。所有 PEI 服务通过 EFI_PEI_SERVICES 服务表提供，除 PPI Services 外还包括 Boot Mode 服务(GetBootMode/SetBootMode)、HOB 服务(CreateHob/GetHobList)、Firmware Volume 服务(FfsFindNextVolume/FfsFindNextFile/FfsFindSectionData)、PEI 内存服务(InstallPeiMemory/AllocatePages/AllocatePool) 等。HOB(Hand-Off Block) 是 PEI 阶段构造的、位置无关的数据结构链表，用于把 PEI 的成果（内存资源描述、固件卷位置、启动模式等）单向传给 DXE：DXE Core 启动时遍历 HOB list 建立全局状态。简单记忆：PPI 解决"PEI 内部横向互相调用"，HOB 解决"PEI 向 DXE 纵向传递信息"。
R: PI_Spec_1_8_A_final_2024.03.05.pdf Volume I: I-6.7 PEIM-to-PEIM Interfaces (PPIs)、I-7.2 PEI Services Table、I-8.2 PPI Services、I-8.4 HOB Services; tianocore-wiki.github.io/development/design-architecture/pi_boot_flow.md PEI Phase 段

Q: Boot Services 和 Runtime Services 有什么区别？ExitBootServices() 被调用后系统状态发生什么变化？
A: 两者都是 EFI System Table 里的函数表，区别在生命周期。Boot Services（UEFI 规范第 7 章：Event/Timer/TPL、内存分配、Protocol Handler、Image Services、杂项）只在 pre-boot 环境有效，OS loader 调用 ExitBootServices() 后一律不可再用。Runtime Services（第 8 章：变量服务、时间服务、SetVirtualAddressMap、ResetSystem、GetNextMonotonicCount、capsule 等）在 OS 运行期仍可调用。ExitBootServices() 的约定：OS loader 先 GetMemoryMap() 取得 MapKey 并立即调用 ExitBootServices(MapKey)，两次调用之间内存图不能变；MapKey 不对则返回 EFI_INVALID_PARAMETER，需重新 GetMemoryMap 再来。固件保证的处理顺序：先调用 EFI_EVENT_GROUP_BEFORE_EXIT_BOOT_SERVICES 事件组 handler → 停掉 timer 服务 → 调用 EVT_SIGNAL_EXIT_BOOT_SERVICES 类型事件和 EFI_EVENT_GROUP_EXIT_BOOT_SERVICES 组的 handler（驱动在此做清理）。成功返回后：OS loader 拥有系统全部可用内存，EfiBootServicesCode/EfiBootServicesData 类型内存可被 OS 回收复用；System Table 的 ConsoleInHandle/ConIn/ConsoleOutHandle/ConOut/StandardErrorHandle/StdErr/BootServicesTable 全部置 NULL 并重算 32-bit CRC；看门狗定时器关闭。此后不得再调任何 Boot Service 和基于 handle 的协议。Runtime 驱动还要处理 SetVirtualAddressMap 时的 EVT_SIGNAL_VIRTUAL_ADDRESS_CHANGE 事件做指针转换。
R: UEFI_Spec_Final_2.11.pdf 7.4.6 ExitBootServices()、8.1 Runtime Services Rules and Restrictions、2.2.2 Runtime Services; tianocore-wiki.github.io/development/design-architecture/pi_boot_flow.md RT Phase 段

Q: TPL(Task Priority Level) 是什么？有哪几级？RaiseTPL/RestoreTPL 怎么用才不踩坑？
A: TPL 是 UEFI 单线程执行环境下模拟"中断优先级"的同步机制。对固件之外暴露四个级别：TPL_APPLICATION=4（所有正常执行所在级别）、TPL_CALLBACK=8（应用级 notify 函数典型级别）、TPL_NOTIFY=16（同步阻塞 I/O 在此级执行，驱动 notify 函数常用）、TPL_HIGH_LEVEL=31（屏蔽一切异步通知，固件内部使用）。事件 notify 函数按 NotifyTpl 分别排入 FIFO 队列，只有当前 TPL 低于队列级别时函数才被执行——因此 RaiseTPL(TPL_NOTIFY) 可以屏蔽 CALLBACK/NOTIFY 级别的通知来保护临界区数据。使用规则：只能升不能降，NewTpl 低于当前级别时行为未定义；RaiseTPL 返回旧 TPL，退出前必须配对 RestoreTPL 恢复；高于 TPL_APPLICATION 的运行时间必须尽可能短，否则可能出现不可预期行为；高于四级的取值保留给固件，用了同样行为未定义。TPL 还限制可调用的服务（规范 7.1 节的表格列出每个服务允许的 TPL 上限）：例如 WaitForEvent() 只能在 TPL_APPLICATION 级调用，Variable Services 要求 ≤ TPL_CALLBACK。在事件 notify 函数（运行在 TPL_CALLBACK/NOTIFY 级）里调任何服务前都要先查这张表。
R: UEFI_Spec_Final_2.11.pdf 7.1.8 RaiseTPL()、7.1.9 RestoreTPL()、7.1 节 TPL 限制表

Q: 分配内存用 AllocatePages 还是 AllocatePool？EfiLoaderData / EfiBootServicesData / EfiRuntimeServicesData 这些内存类型怎么选？
A: 两个都是 Boot Services：AllocatePages(Type, MemoryType, Pages, &Memory) 按 4KiB 页分配，Type 支持 AllocateAnyPages（任意地址）/AllocateMaxAddress（不超过指定地址）/AllocateAddress（指定地址），配对 FreePages()；AllocatePool(MemoryType, Size, &Buffer) 分配任意字节数的池内存，配对 FreePool()。大块内存或有地址要求的用 Pages，小块零碎的用 Pool。MemoryType 决定这块内存的生命周期和归属：EfiLoaderCode/Data 给 UEFI OS loader 的代码和数据；EfiBootServicesCode/Data 是 Boot Services 驱动的代码/数据（Boot Services 驱动分配 pool 的默认类型），ExitBootServices 之后整片可被 OS 回收；EfiRuntimeServicesCode/Data 是 Runtime 驱动的代码/数据，OS 与 OS loader 必须保留，运行期继续可用；EfiConventionalMemory 是空闲内存；EfiReservedMemoryType、EfiACPIMemoryNVS、EfiMemoryMappedIO 等是固件保留区域。选型经验：boot 期临时数据用 EfiBootServicesData；要活到 OS runtime 的（runtime 驱动全局变量、要交给 OS 的表）必须用 EfiRuntimeServicesData；写 OS loader 时用 EfiLoaderData。对应地，ExitBootServices 后固件不得再碰 BootServices 类型内存，OS 必须按内存图保留 RuntimeServices 类型内存。
R: UEFI_Spec_Final_2.11.pdf 7.2 Memory Allocation Services（7.2.1 AllocatePages()、7.2.3 GetMemoryMap()、7.2.4 AllocatePool() 及内存类型定义表）

Q: UEFI 的事件(Event)机制怎么理解？EVT_TIMER、EVT_NOTIFY_SIGNAL、EVT_SIGNAL_EXIT_BOOT_SERVICES 各是什么意思？
A: 事件是 UEFI 唯一的异步原语。事件只有 waiting / signaled 两个状态：CreateEvent(Type, NotifyTpl, NotifyFunction, NotifyContext, &Event) 创建后为 waiting；被 signal 后转 signaled，若 Type 带 EVT_NOTIFY_SIGNAL，则把 notify 函数按 NotifyTpl 放入对应 TPL 的 FIFO 队列，等当前 TPL 降到该级别之下才真正执行（与 TPL 机制联动）。常用 Type：EVT_TIMER——配合 SetTimer(Event, TimerPeriodic/TimerRelative/TimerCancel, TriggerTime) 做周期或一次性定时（TriggerTime 单位 100ns），驱动轮询硬件、超时处理都靠它；EVT_NOTIFY_WAIT——notify 函数在有人 WaitForEvent()/CheckEvent() 等待该事件时被调用，与 EVT_NOTIFY_SIGNAL 互斥；EVT_SIGNAL_EXIT_BOOT_SERVICES——ExitBootServices() 时被 signal，驱动在 notify 里释放必须在 boot 期结束的资源；EVT_SIGNAL_VIRTUAL_ADDRESS_CHANGE——SetVirtualAddressMap() 时 signal，runtime 驱动在此转换指针。不带任何 NOTIFY 标志的是纯等待型事件，用 WaitForEvent 阻塞等待或 CheckEvent 轮询，SignalEvent 可手动触发，CloseEvent 销毁。CreateEventEx 额外支持事件组(EventGroup)：组被 signal 时组内所有事件一起触发，常用组如 gEfiEndOfDxeEventGroupGuid、EFI_EVENT_GROUP_EXIT_BOOT_SERVICES。

Q: UEFI 变量(Variable)服务怎么用？GetVariable/SetVariable 的 Attribute 各是什么意思？
A: 变量是固件提供的、按 (VendorGuid, Name) 索引的键值存储，属 Runtime Services，OS 下也能访问。读用 GetVariable(VariableName, VendorGuid, &Attributes, &DataSize, Data)，标准两段式：先传 DataSize=0、Data=NULL，函数返回 EFI_BUFFER_TOO_SMALL 并给出所需大小，分配缓冲后再调一次。写用 SetVariable(VariableName, VendorGuid, Attributes, DataSize, Data)，DataSize=0 且不加 APPEND_WRITE 时删除变量；遍历变量用 GetNextVariableName()。Attribute 常用位：EFI_VARIABLE_NON_VOLATILE(0x1) 掉电保留（写入 NVRAM）；EFI_VARIABLE_BOOTSERVICE_ACCESS(0x2) boot 服务期可访问；EFI_VARIABLE_RUNTIME_ACCESS(0x4) OS 运行期可访问，必须与 BS 位同用；ExitBootServices 之后没有 RT 位的变量 GetVariable 返回 EFI_NOT_FOUND。EFI_VARIABLE_APPEND_WRITE(0x40) 追加写；EFI_VARIABLE_TIME_BASED_AUTHENTICATED_WRITE_ACCESS(0x20) 基于时间的认证写（PK/KEK/db 这类安全变量用）。典型组合：NV+BS+RT（要对 OS 可见，如 BootOrder）、NV+BS（固件内部使用）、仅 BS（易失变量，重启即丢）。注意 NVRAM 有容量和擦写寿命限制，QueryVariableInfo() 可查询剩余空间，避免高频写。DXE 驱动使用变量服务前，INF [Depex] 要声明 gEfiVariableArchProtocolGuid / gEfiVariableWriteArchProtocolGuid 依赖（UEFI_DRIVER 由 UefiEntryPointLib 自动继承该依赖）。

Q: SMM 和 MM 是什么？传统 SMM 驱动(DXE_SMM_DRIVER)和 Standalone MM 驱动有什么区别？
A: SMM(System Management Mode) 是 x86 处理器的特殊运行模式，用于电源管理、硬件控制、OEM 定制代码等对 OS 透明的系统级功能；MM(Management Mode) 是 PI 规范定义的隔离执行环境，Standalone MM 是其更安全的现代实现。二者区别：传统 SMM 驱动 MODULE_TYPE=DXE_SMM_DRIVER，入口遵循 UEFI 规范的 EFI_IMAGE_ENTRY_POINT，在 DXE 阶段加载（挂 gEfiEventDxeDispatchGuid 事件做多轮派发），初始化期间可用 DXE/UEFI/SMM 服务、运行期只能用 SMM 服务，使用 PEI HOB（HOB 只在 boot 期有效），EndOfDxe 之前没有内存保护（PiSmmCore 在 gEfiEndOfDxeEventGroupGuid 才安装 EDKII_PI_SMM_MEMORY_ATTRIBUTES_TABLE）；Standalone MM 驱动 MODULE_TYPE=MM_STANDALONE，入口遵循 PI 规范的 MM_IMAGE_ENTRY_POINT，只能引用 MM 服务，PEI 阶段早期就由 StandaloneMmIpl 加载 StandaloneMmCore 完成两轮派发（第二轮由 gEventMmDispatchGuid 触发、在 SMM 模式下进行），使用 MM 自有的 HOB（整个生命周期有效），派发结束即安装内存属性表实现早期内存保护。MMRAM 之外内存的访问：Standalone MM 必须先通过 MmUnblockMemoryRequest() 声明 "Unblock"（要求 Post-Mem 阶段完成、runtime 可访问且不被 OS 回收），否则 SMM 模式下访问不到。通信上，非 MM 侧写 CommBuffer 并触发 MMI，StandaloneMmCore 会把 CommBuffer 拷入 MMRAM 影子缓冲再调 MMI handler，返回时拷回——handler 只允许访问影子缓冲，这是防 TOCTOU 攻击的关键设计。

Q: 想给固件做一个图形化设置界面(BIOS Setup)，HII 是什么？VFR 文件扮演什么角色？
A: HII(Human Interface Infrastructure) 是 UEFI 的人机界面框架（UEFI 2.11 规范第 33-35 章）。模块向 HII Database 发布资源包供 BDS 阶段的 Form Browser（设置界面浏览器）渲染，资源分四类：Forms（表单，描述要显示什么内容）、Strings（UCS-2 编码文本，被表单引用）、Font/Image（字体和图形）、键盘布局等。VFR(Visual Forms Representation) 是描述 Forms 的源语言：在 .vfr 文件里用 formset/form/oneof/numeric/checkbox 等语法声明界面结构和 question（设置项），question 通过 varstore 绑定到具体存储（通常是变量）；构建时 VFR 编译器把 .vfr 编译成 IFR(Internal Forms Representation) 二进制打进模块，INF 的 [Sources] 段直接列 .vfr 文件即可，就像普通源码。字符串放在 .uni 文件里，用 STRING_TOKEN 引用。运行期数据流：驱动入口用 HiiDatabaseProtocol(HiiAddPackages) 注册 HII 包；用户在 Setup 里读/改设置时，Form Browser 通过 EFI_HII_CONFIG_ACCESS_PROTOCOL 的 ExtractConfig/RouteConfig/Callback 三个回调与驱动交互，驱动在回调里把配置落盘（一般 SetVariable 存成变量）。VFR 的完整语法见 edk2 VFR Specification（BNF 形式），Windows/Linux 下还有配套的 HII Lab 动手实验指南。

Q: UEFI Secure Boot 的原理是什么？和 Trusted Boot(Measured Boot) 有什么区别？
A: Secure Boot（验证启动，verified boot）的核心是"执行前先验证"：每一级固件用一组策略对象（密钥与签名数据库）验证下一级组件的签名，验证通过才执行——相当于把不可信数据(UDI)经完整性验证程序转换成可信数据(CDI)再运行，对应 Clark-Wilson 完整性模型的 C5 规则。信任链从硬件验证的 Firmware[0]（信任根）开始，之后 Firmware[N-1] 验证 Firmware[N]，任何一层验证失败就中止。UEFI 层面的 Secure Boot 通过四组认证变量实现策略：PK(Platform Key) 是平台主密钥，掌管 KEK 的更新；KEK(Key Exchange Key) 掌管签名数据库的更新；db(Authorized Image Database) 存放允许执行的镜像签名/哈希；dbx(Forbidden Image Database) 是禁止列表。加载 UEFI 镜像（OS loader、Option ROM 等）时验签：命中 dbx 直接拒绝，签名链或哈希在 db 内才放行；另有 dbt（时间戳数据库）、dbr（恢复数据库）辅助。Trusted Boot（度量启动，measured boot）不拦截任何组件：它只把下一级组件的哈希度量扩展(extend)进 TPM 的 PCR 寄存器并记入 TCG event log，供事后校验（如远程证明、OS 依 PCR 状态决定是否解封密钥）。两者互补、常组合使用：Secure Boot 保证"不可信的不给跑"，Trusted Boot 保证"跑了什么有据可查"。
R: Understanding_UEFI_Secure_Boot_Chain/overview.md（Integrity Models）、introduction-to-the-secure-boot-chain.md、secure_boot_chain_in_uefi/uefi_secure_boot.md（PK/KEK/db/dbx 验证关系表）
